ABSTRACT

UrbanEye is an AI-assisted civic issue reporting and complaint resolution platform designed to improve the way citizens interact with local civic administration. Traditional complaint workflows are usually fragmented, slow, and poorly tracked. Citizens often register issues through separate channels, receive little visibility into progress, and rarely get structured public communication once a complaint is escalated. UrbanEye addresses this challenge through a unified digital system that supports complaint reporting, categorization, routing, status monitoring, and AI-generated public update content.

The system combines a web application for dashboard access, a mobile application for field-friendly reporting and tracking, a backend API for business logic and persistence, and a FastAPI-based AI service for complaint analysis. When a complaint is filed, the platform captures the title, description, location, and optional image. The AI layer performs rule-based triage with support for language-model-based enhancement, assigns category and priority, suggests the responsible department, and prepares an X-ready social update for official communication workflows.

The platform supports multiple user-facing views, including complaint dashboards, map hotspots, complaint details, administrative statistics, and profile management. The mobile application additionally provides an improved status-centric interface in which residents can quickly determine whether their complaints are pending, in progress, or resolved. A lightweight persistence strategy is used to support both online and fallback operation, allowing the platform to remain demonstrable even when external services are unavailable.

UrbanEye has been developed using Express.js, Prisma, PostgreSQL-ready schemas, FastAPI, React Native with Expo, and Next.js. The project demonstrates how full-stack application engineering and practical AI augmentation can be combined to solve a real-world civic communication and service-tracking problem in a simple, scalable, and user-friendly manner.

Chapter 1: Introduction

1.1 Project Overview

UrbanEye is a full-stack civic complaint management platform that brings together complaint reporting, routing, analytics, AI-assisted triage, and user-facing status tracking in a single system. The core idea behind the project is simple: residents should be able to report a civic problem in one place, receive meaningful visibility into what happens next, and trust that the complaint is being directed to the correct department. At the same time, authorities need a lightweight operational view of complaint trends, priorities, and hotspots so that action can be better coordinated.

The project was developed as a multi-surface application instead of a single website because civic complaint handling naturally involves different stakeholders and environments. The web application supports dashboard-driven review and broader oversight, the mobile application supports quick complaint entry and resident-side tracking, the Express backend provides a structured API and persistence layer, and the FastAPI AI service produces triage intelligence and social communication text. This split makes the solution modular while keeping the user workflow coherent.

1.2 Need for the Project

In ordinary civic workflows, complaint handling suffers from four recurring issues: fragmented reporting channels, weak classification, poor transparency, and delayed communication. A resident may know that an issue such as garbage overflow, streetlight failure, drainage blockage, or water leakage exists, but may not know which department is responsible or whether the complaint has moved beyond initial registration. In many cases, the complaint is acknowledged but not clearly tracked from the citizen’s perspective.

UrbanEye was designed to reduce that uncertainty. By classifying complaints into categories such as sanitation, electricity, water, and roads, the system supports better routing. By maintaining complaint state fields such as pending, in progress, and resolved, the platform gives the resident a more interpretable progress trail. By producing structured dashboards and hotspot views, it also helps turn individual complaints into actionable operational visibility.

1.4 Scope of the Project

The scope of UrbanEye includes user registration and login, complaint submission with text and optional image, AI-assisted complaint analysis, dashboard and hotspot monitoring, mobile complaint tracking, and basic administrative analytics. The system is intended as a robust academic prototype with production-ready patterns in several modules, especially in API structure, data modeling, and fallback handling.

The present scope does not yet include field workforce dispatch automation, actual X publishing credentials, GIS mapping integration beyond a simplified hotspot representation, or a complete role-based workflow engine for department authorities. However, the current architecture is designed in a way that such features can be introduced incrementally.

Chapter 2: Problem Statement

2.1 Problem Definition

Civic service complaint systems often fail not because people are unwilling to report issues, but because the path from complaint to resolution is unclear. A user may file a complaint and then lose sight of what happens next. The responsible department may not be obvious, complaints may not be categorized consistently, and administrators may not have an immediate cross-channel view of the workload. This creates dissatisfaction for residents and inefficiency for authorities.

The problem becomes more serious when manual handling is involved. Without structured category labels, a water complaint may be mixed with road maintenance tasks. Without a priority signal, urgent incidents may be delayed. Without a public communication layer, residents may assume inaction even when internal processing has started. Thus, the core problem is both operational and communicative.

2.2 Existing System Drawbacks

Issue Description Impact
Fragmented Reporting Residents use different channels or ad hoc mechanisms to submit civic issues. Records become inconsistent and hard to track.
Weak Classification Complaints are often stored as plain text without structured category or priority labels. Wrong routing and delayed action.
Poor Status Visibility Users are not clearly informed whether the issue is open, under action, or resolved. Low trust and repeated follow-up requests.
No Communication Support Public-facing updates require manual drafting every time. Slow information flow and inconsistent messaging.
Limited Administrative Insight Authorities cannot easily view hotspots, departmental breakdowns, or recent patterns. Reactive instead of proactive decision-making.

2.3 Proposed Solution

UrbanEye proposes a layered digital system in which complaints move through a structured lifecycle. The user submits a complaint through web or mobile. The backend forwards the essential textual content to an AI service that performs local classification and can optionally enhance output using an LLM. The enriched complaint, along with its department, priority, suggested action, and X-ready social update, is then stored or returned through the backend. The same complaint becomes visible in user dashboards, hotspot summaries, and administrative views.

Instead of treating AI as a separate showcase feature, the project uses it to reduce practical friction in the complaint-routing workflow. The AI component is therefore directly tied to utility: it shortens triage time, standardizes categorization, and supports communication readiness.

2.4 Specific Objectives

  1. To build a complaint registration interface for citizens on both web and mobile platforms.
  2. To design a backend API capable of storing, retrieving, and presenting complaint status information.
  3. To implement an AI-assisted analysis module for category, priority, department, and social update generation.
  4. To provide an administrative dashboard with counts, breakdowns, and complaint hotspot visibility.
  5. To improve trust and transparency through resident-facing complaint status tracking.
  6. To keep the system modular enough for future integration with maps, notifications, and social publishing.

3.2 Feasibility Study

Technical Feasibility

The project is technically feasible because its components rely on stable and well-documented technologies. Express.js is suitable for API development, Next.js is effective for dashboard-driven web interfaces, Expo supports rapid React Native development, and FastAPI is well suited for lightweight AI microservices. The use of Prisma with a PostgreSQL-ready schema further improves maintainability and future expansion.

Operational Feasibility

The proposed system is operationally feasible because the target workflow is understandable to both citizens and authorities. Residents only need to submit a description and location, while authorities or administrators benefit from pre-computed analytics. The AI component reduces manual interpretation rather than introducing extra complexity.

Economic Feasibility

The development stack used in UrbanEye is cost-effective for an academic and prototype-to-deployment transition. Most components are open source or have student-friendly plans. The architecture can initially run in a demo mode using local/mock data and later be upgraded to managed storage and hosted deployment when necessary.

Chapter 5: Implementation

5.1 Application Screens and Working

Web Application

The web application is built in Next.js and functions as the primary dashboard-oriented interface. The landing page presents the civic issue resolution system with complaint snapshots and quick navigation to registration and the operational dashboard. The dashboard combines a reporting panel, complaint cards, hotspot summaries, and administrative overview metrics. This makes the web view suitable for a supervisory or administrative workflow in which multiple complaints must be scanned in a short time.

Figure 5.1.1: Web Home and Dashboard Flow

Mobile Application

The mobile application is designed from the citizen’s perspective. Its screens focus on quick complaint entry, meaningful status visibility, and reduced friction in follow-up. The home screen now highlights complaint counts and X-account readiness, the dashboard emphasizes the proportion of solved and open complaints, and the profile screen stores a preferred X handle. Local complaint persistence is used so that the dashboard remains informative even under fallback conditions.

Chapter 6: Testing

6.1 Testing Strategy

The testing strategy for UrbanEye was based on iterative verification of individual modules, API routes, and client interfaces. Since the project is composed of several independently runnable parts, each layer was checked using the most practical method available: syntax checks for source modules, bundling for frontend validation, complaint-flow API calls for backend behavior, and fallback execution for resilience testing.

The most notable strength of the test cycle was the presence of fallback mechanisms, which ensured the product remained demonstrable even in a constrained environment.

Chapter 7: Summary and Conclusion

7.1 Summary of Work Done

UrbanEye was developed as an integrated civic complaint resolution platform with four major technical layers: web frontend, mobile frontend, backend API, and AI service. The project began with the core requirement of complaint registration and gradually evolved into a more complete civic workflow system that supports complaint analysis, structured routing, resident status tracking, and administrative monitoring.

On the backend side, complaint, authentication, map, and admin routes were organized in Express. The persistence layer was prepared through Prisma models for user and complaint entities, while a mock store ensured that the system remained operable in demonstration mode. On the AI side, a FastAPI microservice was used to generate category, priority, department, sentiment, suggested action, and X-ready update text. The AI flow was deliberately grounded in practical routing utility rather than purely experimental text generation.

The web application presented complaint dashboards and operational summaries, whereas the mobile application focused on a user-friendly citizen journey with complaint reporting, improved status interpretation, and profile-level X account preferences. Together, these components formed a cohesive project that demonstrates the use of full-stack engineering and assistive AI in public-service workflows.

7.2 Conclusion

The dissertation objective of building an AI-assisted civic issue resolution system has been successfully met in the form of UrbanEye. The project demonstrates that even a relatively compact academic system can meaningfully improve complaint handling when structured data, dashboard visibility, and AI-assisted triage are combined. Rather than simply storing complaint text, the system transforms input into actionable and trackable information.

The strongest contribution of the work lies in its workflow integration. Complaint collection, analysis, storage, dashboarding, and communication preparation are not isolated features; they are linked parts of the same service pipeline. This makes UrbanEye a useful foundation for future civic-tech expansion and a strong example of applied software engineering in a public-facing problem domain.

Chapter 8: Limitations and Future Work

8.1 Limitations of the Project

  1. The current complaint intelligence primarily uses rule-based local analysis, with optional LLM enhancement rather than a fully trained domain model.
  2. The complaint status lifecycle is simplified and does not yet include a complete department-side action workflow or staff assignment engine.
  3. The map hotspot layer is intentionally lightweight and not yet connected to a full GIS visualization stack.
  4. The current system supports X-account preference and X-ready content generation, but not direct authenticated publishing to the X platform.
  5. Fallback demo data is still used in some flows to keep the project resilient in local development, which means not every interface always represents real production traffic.
  6. The report cover page still requires final institutional details such as supervisor name, department, and enrollment number before university submission.

8.2 Future Scope

  1. Integration with official civic department dashboards and authenticated authority accounts.
  2. Real-time notifications through email, SMS, and push notification services.
  3. Direct X publishing for approved official communication after human confirmation.
  4. Geospatial clustering and heatmap-based issue prioritization for city-scale deployments.
  5. Machine-learning models trained on historical civic complaints to improve categorization and urgency scoring.
  6. Complaint assignment and field staff tracking for resolution accountability.
  7. Multilingual complaint intake for wider accessibility.
  8. Evidence-based analytics linking recurring hotspots to planning and maintenance policies.
